## 4. Layout Structure Analysis

The `.section-title` CSS:
```css
.section-title {
  font-family: 'Fraunces', Georgia, serif;
  font-size: 1.25rem;
  font-weight: 600;
  color: var(--charcoal);
  margin-bottom: 1.25rem;
  padding-bottom: 0.75rem;
  border-bottom: 2px solid var(--cream);
  display: flex;
  align-items: center;
  gap: 0.5rem;
}
```

The h3 uses `display: flex` but only for icon + text alignment. It occupies the **full row width** (block element). There is **no sibling element to its right** — the flex is internal to the heading (icon + text), not a row-level flex container.

**Recommended notice placement:** Insert a new `<div>` element **between** the `<h3 class="section-title">` and the first `<div class="form-row">` (the vet name/phone row). This positions the notice above the vet fields, below the section heading. The "to the right of the heading" visual effect could be achieved with `float: right` on the notice or by wrapping both in a flex container, but the simplest approach matching the form's existing patterns is a full-width notice block between heading and fields.

## 5. PDF Generation — Confirmed Separate Path

The PDF is generated by `/home/shelter/shelter-apps/server/src/pdfGenerator.ts` using **PDFKit** (programmatic PDF construction, not HTML rendering). Key evidence:

```typescript
// Line 244-249
sectionHeader('Veterinarian Information');
twoColumn('Vet Name/Clinic', app.vet_name, 'Vet Phone', app.vet_phone);

sectionHeader('References');
// ... renders reference data from AdoptionApplication object
```

The PDF is built entirely from structured data fields (`app.vet_name`, `app.vet_phone`, etc.) using PDFKit's drawing API (`doc.text()`, `doc.rect()`, etc.). It has **zero dependency on the web form's HTML markup**.

**Adding notice text to the web form HTML will NOT propagate to the PDF.** The two paths are completely independent.

## 6. Injection Method Recommendation

**Recommended: Static HTML string in the wp:html block.**

Rationale:
- The entire form is a single self-contained wp:html block with inline CSS/JS
- All form text (labels, headings, instructions) is hardcoded HTML — no gettext, no .po/.mo, no dynamic i18n
- EN and ES are separate WP pages with separate copies of the form HTML (not Polylang translation of the same block)
- Making it a WordPress editable block would require splitting the wp:html block, which is fragile and unnecessary for what is essentially a static legal notice
- A custom field would add complexity with no benefit — this text will rarely change

**Implementation approach:** Insert a styled `<div>` with the notice text between the `<h3>` heading and the vet name `<div class="form-row">`, in three places:
1. WP Page 7 raw content (EN notice text) — via WP REST API fetch-then-edit
2. WP Page 339 raw content (ES notice text) — via WP REST API fetch-then-edit  
3. `/home/shelter/shelter-apps/adoption-form.html` (EN notice text) — direct file edit
