# Animal / Featured Six ES Mechanism Diagnosis — 2026-07-07

## Q1 — What Are the Featured Six, and Where Do They Render?

### Template

`front-page.php` splits the page content at `<!-- FEATURED_ANIMALS -->` marker comments and calls `render_featured_animals()` (functions.php:458). [VERIFIED]

### Data Source

**Live VPS API fetch**, not a WordPress CPT query. The function fetches from:

```php
$response = wp_remote_get('http://66.228.37.38/api/featured-slots', array(
    'timeout' => 10,
    'sslverify' => false,
));
```

Response is cached in a **per-language transient**:

```php
$cached = get_transient('4lg_featured_slots_' . (function_exists('pll_current_language') ? pll_current_language('slug') : 'en'));
```

[VERIFIED — functions.php:460–481]

The API (`GET /api/featured-slots`, server.ts:2971) returns enriched slot data from `buildFeaturedAnimalData()` (server.ts:2892), which pulls from:
- `animal_metadata` table (name, breed, age, sex, species)
- `animal_bios` table via `resolveBioText()` (EN + ES bios)
- `animal_media` table (primary photo)
- `behavior_notes` (traits)

**No WordPress CPT is involved.** Animals are not `shelter_animal` posts — they're live API data from the shelter-app's SQLite DB. [VERIFIED]

## Q2 — How Do the Animal Cards Get Spanish Text?

### Mechanism: (c) + (d) — Render-time field selection from a language-agnostic API response that carries pre-translated content

The API returns **both** EN and ES bio variants in every response, regardless of language:

```typescript
return {
    // ...
    bio_en_short: bioEnShort,
    bio_en_long: bioEnLong,
    bio_es_short: bioEsShort,
    bio_es_long: bioEsLong,
    // ...
};
```

[VERIFIED — `buildFeaturedAnimalData()`, server.ts:2955–2958]

The template selects the correct bio at **render time** based on `pll_current_language()`:

```php
$current_lang = function_exists('pll_current_language') ? pll_current_language('slug') : 'en';
if ($current_lang === 'es') {
    $bio_short = !empty($animal['bio_es_short']) ? $animal['bio_es_short'] : ($animal['bio_en_short'] ?? '');
    $bio_long = !empty($animal['bio_es_long']) ? $animal['bio_es_long'] : ($animal['bio_en_long'] ?? '');
} else {
    $bio_short = $animal['bio_en_short'] ?? '';
    $bio_long = $animal['bio_en_long'] ?? '';
}
```

[VERIFIED — functions.php:508–514]

ES falls back to EN if the ES bio is empty. [VERIFIED]

### Where Do the ES Bios Come From?

The ES bios are **pre-generated by the bio pipeline** using GPT-4o (`translateBioToSpanish()` in attributeParser.ts:429). They're stored in the `animal_bios` table alongside the EN bios and served by the API. [VERIFIED — `resolveBioText()` at server.ts:2858–2890 reads `bio.bioEsLong` and `bio.bioEsShort`]

## Q3 — Are Animal Cards Polylang-Language-Filtered?

**No.** The animal cards are **language-agnostic in their data source** — the API fetch (`/api/featured-slots`) does NOT pass a language parameter. The same 6 animals appear on both EN and ES pages. [VERIFIED — the `wp_remote_get` call has no `lang` param]

The only language-aware parts are:
1. **Bio field selection** at render time (`$current_lang === 'es'` → use `bio_es_*`) [VERIFIED]
2. **Transient cache key** is per-language (`4lg_featured_slots_en` vs `4lg_featured_slots_es`) — but the cached DATA is the same, it's the rendered OUTPUT that differs per language [INFERRED — the transient stores the raw API slots, not rendered HTML, so the per-language key is actually redundant for the data but separates cache invalidation]
3. **UI labels** via `__()` [VERIFIED]

This is fundamentally different from events/stories, which use **Polylang per-post filtering** (`'lang' => pll_current_language('slug')` in their `get_posts` query). Events/stories show DIFFERENT posts per language. Animals show the SAME data with field-level language switching. [VERIFIED]

## Q4 — Reusability Verdict

### The animal mechanism is NOT directly reusable for events/stories.

**Reasons:**

1. **Different data architecture.** Animals are NOT WordPress posts — they're live API data from the shelter-app DB. Events and stories ARE WordPress CPT posts (`shelter_event`, `shelter_story`) queried via `get_posts()` with Polylang's `lang` filter. The animal model (API fetch + render-time field selection) bypasses WordPress entirely. [VERIFIED]

2. **Different content model.** Animals have a single "record" with parallel EN/ES bio fields stored in the same row. Events and stories have user-authored title + rich content (post_title + post_content) that don't have a natural `_es` parallel-field structure in WordPress — WordPress stores one title/content per post. The Polylang model (separate linked posts) is the WordPress-native way to handle this. [VERIFIED]

3. **Different rendering path.** Animal cards are rendered by a PHP function that fetches API data and builds HTML. Events/stories are rendered by template loops that query `get_posts()` and output each post's title/content. Switching events/stories to an API-fetch model would require rewriting their templates AND the dashboard API to serve translated fields. [INFERRED]

### What IS reusable

The **GPT-4o translation infrastructure** (`translateBioToSpanish()` / `translateApplicationFields()` in attributeParser.ts) is directly reusable. It's already proven, callable server-side, and handles EN→ES translation. The event/story push path can call it to translate title/content/etc. before creating the ES WordPress post. [VERIFIED — same OpenAI client, same `getOpenAI()` singleton]

### Why Polylang per-post is still the right model for events/stories

- Events/stories already render via `get_posts()` with `'lang' => pll_current_language()`. The template infrastructure expects separate posts per language. [VERIFIED]
- The existing 6 hand-made ES translations (5 stories + 1 event) already use the Polylang per-post model successfully. [VERIFIED]
- Switching to an API-fetch model would require rewriting `page-events.php` and `page-stories.php` templates, creating new API endpoints for translated event/story content, and abandoning the existing Polylang integration — far more work than adding ES post creation to the existing push handlers. [INFERRED]

### Bottom line

The animal ES mechanism (API-fetch + render-time field selection + pre-translated bios) is a fundamentally different pattern from what events/stories need. It does not transfer. The events/stories plan (create linked Polylang ES posts at push time, using GPT-4o for translation) remains the correct approach. The bio pipeline's translation infra is the reusable piece — the rendering architecture is not. [INFERRED]
